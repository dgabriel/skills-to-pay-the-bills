# Product Requirements Interview

**Inputs:** Idea or brief, existing discovery, audience, and known constraints; no PRD required.
**Output:** Reviewable PRD, default `docs/prd/prd.md`, with assumptions and open questions explicit.
**Try:** “Use product-requirements-interview to define the MVP for my neighborhood tool-sharing app.” (use the skill name in your host's invocation syntax).

Honor the user’s task scope and target-project policy; preserve unrelated work. Use the [procedure](references/procedure.md) for detailed commands/examples and the [shared contract](references/execution-contract.md) when authorization or handoff scope needs clarification.

1. Read existing discovery first; confirm gaps instead of repeating answered questions.
2. Interview in short rounds: problem/users → core experience → scope → success/risks. Reflect answers before advancing.
3. Default to about six or fewer launch must-haves, three explicit non-goals, and one to three observable success signals. Challenge scope with the core journey; adapt counts when the product requires it.
4. Write in the user's language. If asked for an immediate draft, use supplied evidence and labeled proposals; on pause, preserve partial answers and the next open round.

Finish with the artifact or report, checks actually run, open decisions, and the next handoff. Resolve output paths in the target project. See [provenance](PROVENANCE.md) for source revisions and adaptations.
