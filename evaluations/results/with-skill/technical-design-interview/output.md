# BorrowBox technical design — proposed draft

Requirements source: requirements.md. No existing stack exists. Scope: one building, 30 residents, web only, $20/month; listings, requests, owner decisions, borrower returns; accepted date ranges cannot overlap. Exclude payments, chat, insurance and realtime.

## Architecture and rationale
Use FastAPI routers, async SQLAlchemy, Postgres, Alembic, pydantic-settings, and React/TypeScript. FastAPI supplies validated request/response endpoints; Postgres provides transactional booking constraints; SQLAlchemy and Alembic provide explicit data access and versioned schema. React serves a small responsive UI. Serve the compiled frontend with the backend on one small service and use one Postgres database; no queue, cache, websocket service or microservices. Poll booking status on page entry/manual refresh. This keeps the operational surface small. Hosting provider remains open; obtain actual service/database/backup/domain costs and confirm total ≤$20 before provisioning. No provider price or availability is assumed verified.

## Data and transactional invariants
Resident(id, email unique, password_hash, active, created_at); Tool(id, owner_id FK Resident, title, description, active); Booking(id, tool_id FK Tool, borrower_id FK Resident, start_date, end_date, status, created_at, returned_at nullable). Propose statuses pending → accepted/rejected and accepted → returned. Only active members access the site. Only a tool owner decides its requests; only its borrower marks return. Returning twice is idempotent and preserves the original timestamp. Tool owners cannot be forged via client fields; derive ownership and borrower identity from the session.

Propose half-open local calendar ranges [start_date,end_date), CHECK start_date < end_date; date convention and building timezone require confirmation. Reject self-borrowing as a proposed product rule pending review. No cancellation state is assumed implemented without a product decision.

Enforce non-overlap in Postgres with a GiST exclusion constraint on (tool_id WITH =, daterange(start_date,end_date,'[)') WITH &&), restricted to status='accepted'; provision btree_gist via migration if permitted by the chosen host. Acceptance runs in one transaction: lock target booking and tool row, verify actor ownership and pending status, then update to accepted. All acceptance paths must acquire the same tool lock; constraint remains defense in depth. Concurrent overlapping acceptances yield one success and one 409, with rejected transaction rolled back. Adjacent ranges can both succeed. Pending requests may overlap. Return atomically updates status and timestamp. Whether late returns should block future reservations beyond the planned interval is an unresolved policy; the date constraint alone cannot ensure physical availability.

## Access and interfaces
Propose invite-only accounts using admin-created invitations, email identity, hashed passwords via a maintained library, and opaque server sessions in HttpOnly/Secure/SameSite cookies; require CSRF protection on mutations and login throttling. Auth method is proposed, not accepted. Password reset can initially be an administrator-assisted flow with single-use expiring reset tokens; confirm administrative ownership and usability before launch. No outbound email dependency is required for the pilot; invitation links can be shared manually by the administrator. Store only minimal membership information, never log credentials/tokens.

GET /tools; POST /tools; PATCH /tools/{id} (owner only); POST /tools/{id}/requests; GET /bookings (actor's borrowing and owned-tool requests); POST /bookings/{id}/accept; POST /bookings/{id}/reject; POST /bookings/{id}/return. Include login/logout and invite redemption endpoints. Authenticate each route and enforce authorization server-side before any write. Validate date/body fields; 401 for no session, 403 for forbidden actors, 404 for absent resource, 409 for overlap/invalid transition, 422 for invalid dates. Return field-specific actionable errors without SQL/internal details. Scope GET responses to building members and avoid exposing unnecessary emails. Database failures roll back and produce a retryable generic error; UI preserves form input and re-fetches uncertain outcomes before retrying.

## Configuration and operations
Use pydantic-settings for DATABASE_URL, SESSION_SECRET, ALLOWED_ORIGINS, PUBLIC_BASE_URL, BUILDING_TIMEZONE, INVITES_ENABLED and LOG_LEVEL; document keys without secrets. Keep feature flags environment driven and few. HTTPS termination at the chosen host, database network restrictions, dependency updates, health/readiness endpoints, structured redacted logs, and error monitoring via logs are sufficient initially.

Propose daily encrypted database backups retained seven days and a prelaunch restore drill. Proposed RPO 24 hours and RTO one working day need owner acceptance. Use a short announced maintenance window for migrations. Verify Alembic upgrade → downgrade → upgrade where reversible on a disposable database, constraint presence, and restore compatibility. For irreversible migrations use a reviewed forward recovery/backup plan. Resident removal deactivates access; tool deletion with live bookings is restricted; personal-data retention/anonymization schedule remains a decision, not an invented promise.

At 10× (300 residents), first investigate DB connection count, list pagination/indexes, and resource usage on the budget host; measure before adding infrastructure. The budget may become the first operational limit. Provider selection and extension support remain launch prerequisites.

## Acceptance and test gates
Verify the full listing → request → owner decision → borrower return journey through API and browser. Test non-owner decisions return forbidden and leave state unchanged; missing/invalid requests; both date adjacency orders; overlapping concurrent acceptance (one success only); disjoint concurrent acceptance; repeated decisions/returns; borrower isolation; inactive-member access; CSRF/session expiry. Use isolated Postgres integration tests for constraints and concurrency rather than SQLite substitutes, and frontend checks for keyboard navigation and error recovery. Run migrations and backup restore in a disposable environment. No tests, migrations or deployments were executed for this design-only task.

## Decisions and handoff
Reject SQLite for this proposal because database-enforced concurrent non-overlap is valuable; reject queues/realtime because no requirement needs them; reject an external email dependency for the initial pilot to protect cost and setup simplicity. Scope deliberately omits advanced search, notifications and admin dashboards. All choices remain proposed. Confirm date semantics, auth/admin ownership, hosting cost/extension support, late returns, retention and recovery tolerance before implementation. Static consistency review performed against supplied requirements; no external verification or code changes. Handoff artifact: this output.md and requirements.md, with the above unresolved prerequisites.
